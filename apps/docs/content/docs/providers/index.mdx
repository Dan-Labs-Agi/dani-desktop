Every production bot runs through Hermes Agent. Choose a hosted or local model from Hermes' configured providers; model choice is independent of the bot's harness. If Hermes or a selected model is unavailable, DaniBot does not silently start a different agent CLI.


## Internal driver integrations

| Engine | Authentication shape | Notes |
|---|---|---|
| Claude | Claude CLI login | Strong support for tools, approvals, sessions, and local computer use |
| Codex | Codex CLI login | Model discovery, approvals, steering, and computer tools |
| Grok | Grok CLI login | ACP-based local model catalog and session support |
| Cursor | Cursor Agent CLI login or API key | ACP driver with live model discovery |
| GitHub Copilot | `copilot login`, or `COPILOT_GITHUB_TOKEN` | ACP driver with the plan's live models, each labelled with its premium request multiplier |
| Kimi | Kimi CLI login | ACP integration |
| Droid | Factory Droid CLI login | ACP integration |
| Antigravity | Google account through the official ACP server | Managed install, isolated accounts, live models, and approval cards |
| OpenCode | Existing OpenCode provider login or optional API key | Live Zen, Go, third-party, and local model discovery through ACP |
| Qwen | Qwen CLI login | ACP integration |
| Hermes | Hermes CLI login | ACP integration |
| Pi | Pi CLI login | Native driver |

The integrations below remain in the codebase for provider management and isolated protocol fixtures. They are not alternative production bot harnesses. Configure model access in Hermes; a login or API key saved for another CLI is not automatically transferred to Hermes.

GitHub Copilot runs the official Copilot CLI (`npm install -g @github/copilot`) in its ACP mode and bills the signed-in Copilot plan, unless the CLI is set up to bring its own key: `COPILOT_PROVIDER_*` variables in the `githubCopilot` instance's `environment`, or a `providers.json` in the Copilot CLI home (`~/.copilot`, or `COPILOT_HOME`), send model requests to that provider, which bills them. A `GH_TOKEN` or `GITHUB_TOKEN` in DaniBot's own environment never reaches it, because either would take precedence over the CLI's login; put one in the `githubCopilot` instance's `environment` to use it. `COPILOT_ALLOW_ALL` is always removed, so tool approvals stay with DaniBot.

To use a different model provider, configure it in Hermes and refresh the model catalog. Only provider-qualified Hermes model IDs or supported local-endpoint IDs are routed. A legacy unscoped model must be reselected rather than guessed or replaced with another paid provider.

## Mistral API

Configure Mistral as a model provider in Hermes, then choose the model Hermes advertises. A `mistral.key` setting configures the internal Mistral integration; it does not switch a production bot away from Hermes or automatically export that key into Hermes.

## Detection

DaniBot checks for the Hermes executable. Restart after installing or configuring Hermes. If discovery fails, use its executable-path setting. Installing another agent CLI does not provide a production fallback.

## Model selection

The model picker lists Hermes' configured models and marks its default. Each bot may choose a different model, and a conversation can pin its own model. Changing the model affects future turns without rewriting transcript history. Existing engine-specific effort or variant controls reset when a selection migrates to Hermes.


## Internal native-driver browser contracts

Codex bots use the browser and computer selected in DaniBot. Desktop-only Codex
browser/computer features and their bundled plugins are disabled for those bot
processes, so bots do not select a native desktop connection that is unavailable
inside the CLI. This does not uninstall plugins or change the standalone Codex app.
Native web search keeps its configured mode.

After built-in browser navigation, DaniBot collects a snapshot in the same
browser session. A sign-in page or redirect is evidence of where navigation landed,
not confirmation that the requested task finished. Connection failures retain the
selected computer/account and do not automatically replay uncertain actions.

## Multiple Claude accounts

Open **Settings → Engines → Add Claude account** and give the account a name, such as **Work** or **Personal**. DaniBot creates a separate configuration-directory setting for it; it does not copy your existing login. Under **Manage account and sign-in**, copy the sign-in command and run it on the computer hosting DaniBot, then choose **Check account**. On Windows, use PowerShell. Claude handles the browser sign-in and stores its own credentials.

In a bot's model picker, choose **Claude**, select **Work** or **Personal** in the **Account** dropdown, then choose a model to save the selection. Claude appears only once in the provider list. Each bot keeps its own selection, and the chat header shows the account name. Account changes apply to future turns and are blocked while that bot is responding; other bots are unaffected. Conversation history is not erased when you change the selection.

The original **Default** entry keeps using your existing CLI login. Advanced users can supply an existing, separate Claude configuration directory. Once an account has been used by bots or conversation history, add a new account instead of repointing its directory. Removing an account from DaniBot does not delete its files or sign it out; first move any bots using it to another account.

This does not require a CLI proxy, and there is no automatic account rotation or fallback. Named account management currently supports Claude only.

<Callout type="info" title="Subscriptions stay with the provider">
  Your existing CLI login or provider API key determines access and billing. DaniBot does not turn one subscription into access to another provider.
</Callout>
