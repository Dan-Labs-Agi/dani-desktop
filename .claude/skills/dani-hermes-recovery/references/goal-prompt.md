## 4. Retry and recovery policy

Classify the failure before deciding what to do:

- Stale selector/reference or observation mismatch: obtain a fresh current snapshot, identify the intended target again, and retry a safe observation/action within a bounded policy.
- Transient transport/provider failure: bounded backoff with cancellation/deadline awareness; retain the original request and progress.
- Wrong endpoint/protocol, unsupported tools, missing credentials or deterministic configuration error: fix the configuration or show an actionable genuine blocker. Repeating the same 404 five times is not resilience.
- Browser disconnect/backend restart: restore the authorized session and inspect current state before continuing; do not create duplicate goals or silently switch threads.
- Unknown consequential outcome: inspect receipts and authoritative external state before replay. At-least-once delivery does not guarantee exactly-once effects.
- Human control, explicit Stop, denied permission or revoked capability: honor the boundary immediately. Resume only when the required authority actually returns.

The model must not claim success for an unknown effect or silently switch provider/model to hide failure. Retry policy must have measured outcomes and negative tests, not merely more retry counters.
