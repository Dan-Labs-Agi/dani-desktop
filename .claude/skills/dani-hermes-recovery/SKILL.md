# DANI Hermes recovery

## Authority

This is a user-invoked transfer skill, not an autonomous instruction to restart a stopped campaign. The previous assistant was explicitly stopped. Authoring or reading this package alone does not authorize implementation, inference, deployment, publication, account changes, or live-data mutation.

When the user invokes the accompanying goal in a replacement harness, use this procedure. Preserve the existing application and dirty working tree. Use isolated owned fixtures for mutation verification. The user's explicit Stop always wins.

## 1. Establish ownership and a concrete bar

1. Read the repository's applicable instructions, `docs/verification/README.md`, current package scripts and the ledger's preservation boundaries.
2. Establish the exact source/candidate identity and owned processes/data. Preserve pre-existing changes; do not infer authorship or reset the tree.
3. Separate observed facts, failed checks, unverified edits and external blockers. A source report, catalog, compiled package or task checkbox is not native acceptance.
4. Tell the user which concrete defect is first, which surface will be exercised, and what observable result closes it. Then work; do not ask them to repeat repository-provided facts.

**Completion criterion:** one inspectable acceptance ledger with every requested gate, exact artifacts, known RED evidence, independent owners and explicit authority boundaries.

## 2. Trace the real execution path

Follow the actual chain: renderer request → original request/goal owner → native Hermes launch/session/model → active tool inventory → broker/driver → external effect → evidence → original-request settlement.

Preserve the later verified native-policy, browser-ownership and broker repairs. The remaining native-desktop proofs include executed same-session continuation and visible rejection of a wrong-nonce qualification that actually reaches inference.

Review the separate candidate's unverified companion-header, release-CI and HPKE-v1 edits before adoption. Existing rebranded-v1 client support makes the crypto restoration a compatibility decision, not a golden-vector-only fix.

Keep generic sealed fixtures separate from native-Hermes admission tests. Canonical fixture repair must not reintroduce a production raw-CLI bypass.

**Completion criterion:** the real boundary causing each selected failure is identified, and the next proof can fail on that exact defect without changing live user state.

## 3. Build one coherent slice

- Reuse the existing durable coordinator and native Hermes APIs. Keep one owner for each goal, session, gateway and effect path.
- Use observed RED evidence or a meaningful failing regression before production edits. Do not rerun a user-reported failure just to confirm it.
- Apply the smallest maintainable fix. Preserve exact provider/model identity, MCP capabilities, Stop/denial, pending-owner settlement and unknown-effect handling.
- Keep browser-only work inside its admitted managed browser. Full native coding is intentionally broader and must not be misrepresented as an OS sandbox.
- Freeze the slice before its checks. Permanent tests cover behavior, boundaries and transitions; throwaway smoke proves integration. Delete incidental wording/source-text assertions instead of repinning them.

**Completion criterion:** focused GREEN and an actual exercised changed path, with raw evidence and no regression of the relevant negative cases.

## 4. Run an independent Gauntlet

Delegate only substantial independent workstreams with exclusive ownership and explicit interfaces. The integration owner keeps the full goal and runs the assembled checks. Use the replacement harness's actual concurrency limit; queue waves rather than pretending a requested worker count proves quality.

A fresh critic receives the exact criteria, real artifact and inspectable evidence, not builder rationale or self-scores. The builder never awards acceptance.

Require this critic response:

```text
Gate verdicts: PASS/FAIL with evidence
Overall: PASS/FAIL
Largest meaningful gap: one observed gap
Next proof: one concrete artifact or scenario
Invalid or missing evidence:
Uncertainty and surviving risks:
```

Fix the largest evidenced gap, preserve the best-known accepted state, and use a new critic context each round. Whole-product integration gets its own fresh critic; component passes cannot average away a failed gate.

The loop continues while authorized, evidence-producing work remains. It ends on verified PASS, a precise external BLOCKED state, evidence-backed PLATEAU, or explicit user/resource Stop. Two worsening attempts reject a prescription; at most two materially distinct strategy resets precede PLATEAU. After PASS, wait for approved triggers rather than generating speculative changes or continuous paid polling.

**Completion criterion:** independent gate verdicts and one current integration verdict, never an aggregate self-assigned score.

## 5. Deliver the real application

Exercise the current Electron candidate with real renderer/preload/backend/Hermes/browser. Include a real native coding task and a supervised browser task with independently checked effects. Check model selection and useful failure UX on that same surface.

Keep the existing user app/workspaces and the ownership-ambiguous shared acceptance root out of mutation tests. Reuse the later exercised private launcher only after inspecting its current contract, with a new owned root and explicit candidate. A macOS browser/coding fixture does not prove native CUA or Windows.

Run coherent relevant CI, types/lint/build/package gates on the same candidate. Prove a newer installed update only when release/signing/publication authority exists; otherwise state the exact prerequisite separately from local delivery.

Report the actual artifact/URL, what was exercised, which gates passed, remaining blockers, ownership-aware launch/stop instructions, and evidence locations. Remove only owned temporary scaffolding/credential copies after evidence is retained; preserve the user's work.

**Completion criterion:** the user can use the demonstrated local application, or the only remaining blockers are explicitly evidenced external prerequisites. Neither “tests passed” nor “code is implemented” substitutes for this outcome.
